開發部圖面資料申請表｜需求筆記（示範資料，全為虛構）

■ 背景
- 公司：示範公司（虛構）。開發部負責保管圖面、材質證明、測試報告、樣品等技術資料，其他部門需要時向開發部申請調閱。
- 目前做法：手寫紙本單據，或在 LINE 群組喊話申請；主管要回辦公室才能簽核。
- 目前問題：
  - 群組訊息容易漏字、被洗掉，申請內容不完整。
  - 主管出差或不在辦公室時，申請就卡住。
  - 資料零散難追蹤，發放時間沒有紀錄。
  - 口頭退件難掌握，申請同仁常常空等。
- 現有的過渡做法（Google 表單＋Google 試算表＋Apps Script＋LINE）有安全疑慮：核准連結任何人拿到都能按、用姓名對應 LINE ID 容易寄錯人。
- 新系統方向（已決定）：
  - 網頁放在 GitHub Pages，在 LINE 裡開啟（LIFF）。
  - 使用者用 LINE Login 登入，系統依登入身分決定能做什麼。
  - 資料存在 Supabase，用資料列安全（RLS）控制存取。
  - 通知用公司的 LINE 官方帳號（Messaging API），由 Supabase Edge Functions 發送。
- 流程：同仁線上填表（系統自動編號）→ 部門主管審核 → 核發主管放行 → 文管發放 → 已發放結案。任何一關駁回，系統用 LINE 私訊通知申請同仁。

■ 要登記的資訊
（一）申請單：同仁填寫
- 申請人：登入後自動帶入，不用手填。
- 所屬部門：下拉選單。目前選項為 品管課、採購課、業務部、其他（是否加入開發部待確認）。
- 申請資料別：可複選，選項為 圖面、材質證明、測試報告、樣品。
- 品號／零件名稱／規格：多行文字，一行一筆，可一次填多筆。
- 申請用途：下拉選單，選項為 提供給客戶、廠商詢價或發包、現場組裝或試作、品管進料或出貨檢驗、設計參考、其他。
- 需求格式：可複選，選項為 2D PDF、2D DWG或DXF、3D STEP或STP、3D 原始檔、紙本或實體、其他。
- 預計外發對象／備註說明：多行文字，選填。

（二）申請單：系統自動產生或更新
- 單號：格式 DOC-yyyyMMdd-3碼流水號，例如 DOC-20261112-001，每天從 001 重新編號。
- 申請時間：送出時自動記錄。
- 外部用途標記：用途為「提供給客戶」或「廠商詢價或發包」時自動標記，在清單與通知中特別顯示。不加審核關卡。
- 案件狀態：申請主管簽核中、核發主管簽核中、待文管發放、已發放結案、已駁回。
- 部門主管簽核：結果（待簽核／已核准／已駁回）、簽核人、簽核時間。
- 核發主管簽核：結果（待第一關簽核／待簽核／已核准／已駁回）、簽核人、簽核時間。
- 發放紀錄：發放方式（Email、雲端連結、紙本或實體、其他）、發放人、發放完成時間。不記錄版次。

（三）簽核紀錄（每個動作一筆，只能新增）
- 單號、動作（送出、核准、駁回、發放）、執行人、時間、備註。

（四）設定資料
- 使用者：LINE 登入後綁定，記錄顯示名稱、所屬部門、角色。
- 部門主管設定：每個部門對應一位部門主管。
- 核發主管：一律為開發部主管。
- 文管人員：可以有多位。

■ 誰能做什麼
- 申請同仁：
  - 可以新增申請。
  - 可以查看自己的申請與進度，不能查看別人的申請。
  - 送出後不能修改；填錯時請主管駁回，再重新填單。
- 部門主管（第一關）：
  - 收到 LINE 通知，可以查看並核准或駁回自己部門的申請。
  - 只有登入身分是該部門主管時才能操作。
- 核發主管（第二關，開發部主管）：
  - 收到 LINE 通知，可以查看並核准或駁回已通過第一關的申請。
- 文管人員：
  - 收到 LINE 通知，可以查看待發放的申請，並記錄發放方式、按「已發放」結案。
  - 多位文管同時按時，只有第一個成功，不會重複結案。
- 系統管理員：維護使用者角色、部門主管設定與文管人員名單（由誰擔任待確認）。
- 每一關只能依順序進行：沒通過第一關不能進第二關，已駁回或已結案的申請不能再操作。

■ 資料安全
- 這是示範：文件、範例資料與截圖一律使用虛構的姓名、部門、品號與客戶，不放真實資料。
- 所有頁面都要先用 LINE 登入；未登入的訪客不能讀取或新增任何資料（與報修示範不同，不開放匿名存取）。
- 資料表全部啟用資料列安全（RLS），依登入身分與角色決定能讀哪些資料。
- 狀態變更（核准、駁回、發放）只能透過資料庫函式進行，函式內檢查執行人的角色與案件目前狀態；前端不能直接修改狀態欄位。
- 核准或駁回必須由已登入的本人按下按鈕送出，不靠網址參數判斷身分，避免 LINE 預覽網頁時誤觸。
- 簽核紀錄只能新增，不能修改或刪除。
- 前端只能使用 Supabase publishable key。
- Supabase secret key、LINE Channel secret、LINE Channel access token 只能存在 Supabase 後台的機密設定（Edge Functions secrets），不能寫進任何檔案或提交到 GitHub。
- 系統不存放圖檔本身，只記錄申請、簽核與發放狀態。
- 真實的 LINE User ID 屬於個人資料，不寫進文件或範例資料。

■ 還沒決定的事
- 「申請資料別」「申請用途」「需求格式」是否改為必填（目前 Google 表單為選填）。
- 部門、用途、格式選「其他」時，是否要另外填寫說明。
- 部門選項是否加入開發部，以及完整的部門清單。
- 是否新增欄位：需要日期、版次、份數。
- 駁回時是否必須填寫原因。
- 申請同仁能否在主管簽核前自行撤回申請。
- 部門主管能否查看自己部門所有人的申請；核發主管與文管能否查看全部申請。
- 部門主管本人提出申請時，第一關由誰簽核。
- 主管請假或出差時的代理人。
- 簽核逾時是否要提醒。
- 系統管理員由誰擔任。
- LINE Login 與 Supabase 登入的整合方式（需要先做技術驗證）。
- LINE 官方帳號的訊息費用與每月免費則數是否足夠。
- 現有 Google 試算表的舊資料是否要匯入新系統。
- 是否需要統計報表或匯出 Excel。
